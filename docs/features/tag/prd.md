# 태그 기능 PRD

> 근거 문서: [`spec-fixed.md`](./spec-fixed.md) (확정 정의서). "기술 결정" 섹션은 ADR-001 하나를 채웠고, 추가 결정이 생기면 ADR을 이어서 쓴다.

## 1. 개요

### 배경

노트가 늘어나면 성격이 다른 노트를 구분할 수단이 없다. 노트에 짧은 키워드(태그)를 붙일 수 있게 해, 이후 분류·검색 기능의 기반 데이터를 마련한다.

### 목표

- 사용자가 노트 편집기(`NoteEditor`)에서 노트에 태그를 추가하고 삭제할 수 있다.
- 태그는 노트와 함께 저장되며, 편집기에서 목록을 확인할 수 있다.

### 비목표

- 태그를 이용한 검색·필터링 등 활용 기능은 이번 범위가 아니다(→ [5. Out of Scope](#5-out-of-scope)).

### 성공 기준

- Enter로 태그가 추가되고, 중복(대소문자 무시, 공백 제거)과 빈 값은 추가되지 않는다.
- 칩의 `X`로 해당 태그만 삭제된다.
- 저장 시 PATCH/POST 본문에 `tags`가 포함되고, 취소 시 태그 변경이 버려진다.
- `tags`가 없는 기존 노트를 열어도 오류 없이 빈 태그로 표시된다.
- 한글 입력 후 Enter 시 태그가 한 번만 추가된다.

| ---- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |

| US-3 | 노트 작성자로서, 잘못 붙인 태그를 삭제하고 싶다.                                         | 칩에 hover(또는 키보드 focus)하면 `X`가 나타나고, 누르면 해당 태그만 제거된다.                                          |

| US-7 | 키보드 사용자로서, 마우스 없이도 태그를 삭제하고 싶다.                                   | `X` 버튼이 `focus-visible`에서도 보이고 `aria-label`(`"{태그} 태그 삭제"`)을 가진다.                                    |

## 3. 기술 결정

### ADR-001: 커스텀훅 합성 기반 태그 상태 관리

- **상태**: 제안됨 (아키텍처 3안 비교 후 사용자가 "안 C"의 훅 기반 방향을 선택. 저장 시점은 확정 정의서를 유지)

#### Context

- 확정 정의서는 태그를 `NoteEditor`의 로컬 폼 상태로 들고 있다가 저장 버튼에서 `title`/`content`와 함께 저장하도록 정했다(추가/삭제 즉시 서버 요청 없음, 취소 시 폐기).
- 태그 로직은 `title`/`content`보다 복잡하다. 정규화(trim + 대소문자 무시 중복 판정, 표기 유지), 빈 값 무시, 입력창 임시 텍스트, 한글 IME 조합 중 Enter 무시, Enter의 submit 방지가 모두 필요하다.
- 현재 `NoteEditor`는 폼 상태를 `useState` 3개로 직접 들고 있고, 프로젝트에는 `hooks/` 디렉터리와 커스텀훅이 없다. 컴포넌트 규칙은 "컴포넌트는 UI 상태와 렌더링만 맡고, 데이터 접근은 `useNotes()`로만 한다"이다.
- 이 로직을 인라인으로 두면 `NoteEditor` 전체를 렌더링해야만 테스트할 수 있고, 이후 기능이 붙을수록 컴포넌트가 비대해진다.
- 팀(사용자)은 React 순정 API(`useState`, `useEffect` 등)와 커스텀훅 합성을 선호하며, 이후 컴포넌트에서도 커스텀훅을 더 활용하는 방향을 원한다.

#### Decision

React 내장 훅만으로 만든 커스텀훅을 합성한다. 외부 상태 라이브러리와 `useReducer`는 쓰지 않는다.

- **`useTags(initialTags)`** (`src/hooks/useTags.ts`)
  - `tags` 상태와 `addTag(raw)`, `removeTag(tag)`, `resetTags(tags)`를 반환한다.
  - 정규화·중복 판정·빈 값 무시를 이 훅이 책임진다. 저장 값은 공백만 제거한 원래 표기를 유지하고, 추가 순서를 보존한다.
  - 서버나 Context를 모른다. 순수 폼 상태 훅이다.
- **`useTagInput(onAdd)`** (`src/hooks/useTagInput.ts`)
  - 입력창 임시 텍스트와 `onChange`/`onKeyDown` 핸들러를 반환한다.
  - Enter 처리, IME 조합 중(`e.nativeEvent.isComposing`) 무시, `preventDefault`, 추가 후 입력창 비우기를 책임진다.
- **`TagInput` 컴포넌트** (`src/components/TagInput.tsx`)
  - `tags`, `onAdd`, `onRemove`를 props로 받는 표현 컴포넌트. 내부에서 `useTagInput`을 합성해 칩 목록과 입력창을 렌더링한다.
  - `X` 버튼은 hover와 `focus-visible`에서 보이고 `aria-label`(`"{태그} 태그 삭제"`)을 가진다. 스타일은 디자인 시스템 토큰만 쓴다.
- **`NoteEditor`**
  - `useTags`를 호출해 `TagInput`에 연결한다. 선택 노트 변경 시 기존 `useEffect` 안에서 `resetTags(selectedNote.tags ?? [])` 또는 `resetTags([])`를 호출한다.
  - `handleSave`가 `tags`를 함께 보낸다. 저장 시점은 정의서대로 저장 버튼 일괄 저장이다.
- **데이터/API/Context**
  - `Note.tags: string[]`. 읽을 때 `tags ?? []`로 간주한다.
  - `api/notes.ts`의 `createNote`는 `tags`를 선택 인자로 받고 기본값 `[]`를 채운다. 수정은 기존 `updateNote(id, { title, content, tags })`(PATCH)를 쓴다.
  - Context의 `createNote(title, content, tags)`는 위치 인자를 이어 붙인다. Context에 `addTag`/`removeTag`는 만들지 않는다.
- 훅은 Context 값 비메모이제이션 규칙에 맞춰 `useCallback`/`useMemo`를 쓰지 않는다.

#### Alternatives

| 대안                                       | 내용                                                                          | 채택하지 않은 이유                                                                                                                                                                                                                                           |
| ------------------------------------------ | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 안 A: 인라인 최소 확장                     | `NoteEditor` 안에 상태·정규화·IME 처리를 직접 작성 (정의서의 4개 파일만 수정) | 파일 변경은 가장 적지만 정규화와 IME 규칙을 컴포넌트 렌더링 없이 검증할 수 없다. 컴포넌트가 비대해진다.                                                                                                                                                      |
| 안 B: 순수 함수 + 컴포넌트 분리            | `utils/tags.ts`의 순수 함수와 `TagInput`으로 분리, 상태는 `NoteEditor`가 보유 | 정규화 테스트는 쉬워지지만 입력 상태와 IME 처리가 컴포넌트에 남고, 훅 합성 방향과 맞지 않는다.                                                                                                                                                               |
| 안 C 원안: 태그별 즉시 저장                | Context에 `addTag`/`removeTag`를 두고 추가/삭제마다 PATCH                     | 정의서의 ★ 결정(저장 버튼 일괄 저장)을 뒤집는다. 새 노트 모드에서는 `id`가 없어 동작하지 않고, 취소로 되돌릴 수 없으며, 연속 PATCH가 서로 덮어쓸 수 있다. Context 함수 이름 규칙(`create/update/delete + Note`)에서도 벗어난다. 훅 기반이라는 장점만 취했다. |
| 외부 폼 라이브러리 (`react-hook-form` 등)  | 폼 상태를 라이브러리에 위임                                                   | React 순정 API를 쓴다는 방침과 맞지 않고, 의존성이 늘어난다. 태그 하나를 위해 과하다.                                                                                                                                                                        |
| `useReducer` 또는 Context로 태그 상태 관리 | 태그 상태를 리듀서나 전역 상태로 관리                                         | 프로젝트 컨벤션(`useReducer` 미사용, 폼 입력은 로컬 상태)과 충돌하고, 태그는 편집기 밖에서 쓰이지 않는다.                                                                                                                                                    |

#### Consequences

**장점**

- 정규화·중복·빈 값·IME 규칙을 `renderHook` + `act`로 DOM 없이 단위 테스트할 수 있다. 훅 두 개가 서로 독립적이라 각각 따로 검증된다.
- `NoteEditor`는 훅을 연결하고 저장만 담당하므로 비대해지지 않는다. `TagInput`은 `useTagInput`을 바꿔 끼우면 다른 화면에서도 재사용할 수 있다.
- 저장 시점이 정의서와 같아 PRD의 사용자 스토리 US-1~7과 충돌이 없다.
- 이후 `title`/`content`/`saving`도 `useNoteForm` 같은 훅으로 합성해 갈 수 있는 길이 열린다.

**단점 / 비용**

- 정의서의 변경 대상 4개 파일 외에 신규 파일 3개(`useTags.ts`, `useTagInput.ts`, `TagInput.tsx`)가 생긴다.
- 프로젝트에 없던 `src/hooks/` 디렉터리가 생기므로 `CLAUDE.md`의 아키텍처·컨벤션 섹션에 훅 규칙을 추가해야 한다.
- 당분간 폼 상태가 두 방식으로 갈린다. `title`/`content`는 `NoteEditor`의 `useState`, `tags`는 훅이다. 요청 없이 기존 상태를 일괄 변환하지 않는다는 규칙에 따라 이번에는 `tags`만 훅으로 만든다.
- 기존 이슈가 그대로 남는다. 서버에서 노트가 갱신돼도 폼이 다시 동기화되지 않으며(`useEffect` 의존성이 `selectedNoteId`, `isCreating`뿐), `resetTags` 호출은 이미 `eslint-disable`로 억제된 그 `useEffect`에 추가된다.
- 훅 단위 테스트가 컴포넌트의 연결 오류를 잡아주지 않으므로, `NoteEditor`의 저장 시 PATCH 본문에 `tags`가 포함되는지는 별도의 컴포넌트 테스트가 필요하다.

**후속 확인 필요**

- `spec-fixed.md`의 두 문장이 어긋난다. 14행은 "호출자는 태그를 따로 넘기지 않는다"이고 43행은 `createNote(title, content, tags)`다. 이 ADR은 후자를 따르며, API는 `tags`를 선택 인자로 받고 기본값을 `[]`로 채운다.

## 4. 용어 정의

| 용어                  | 정의                                                                                                                    |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 태그(tag)             | 노트에 붙이는 짧은 문자열 키워드. 최대 15자. `Note.tags: string[]`로 저장한다.                                          |
| 칩(chip)              | 태그 하나를 표시하는 UI 요소. 삭제용 `X` 버튼을 포함한다.                                                               |
| 정규화(normalization) | 중복 판정을 위해 앞뒤 공백을 제거하고 대소문자를 무시하는 비교 규칙. 저장 값 자체는 공백만 제거한 원래 표기를 유지한다. |
| 중복 태그             | 정규화 결과가 같은 태그. 예: `React`, `react`, `react`.                                                                 |
| IME 조합(composition) | 한글 등을 입력할 때 글자가 확정되기 전의 상태. 이 동안의 Enter는 태그 추가로 처리하지 않는다.                           |
| 로컬 폼 상태          | `NoteEditor`가 보유한 `title`/`content`/`tags` 상태. 저장 버튼을 누르기 전까지 서버에 반영되지 않는다.                  |
| 기존 노트             | 태그 기능 도입 전에 생성되어 `db.json`에 `tags` 필드가 없는 노트. 읽을 때 `[]`로 간주한다.                              |
| `NoteEditor`          | 노트 생성/편집 겸용 폼 컴포넌트. 태그 추가/삭제 UI가 위치한다.                                                          |
| `NoteItem`            | 목록의 노트 카드 컴포넌트. 이번 범위에서는 태그를 표시하지 않는다.                                                      |

## 5. Out of Scope

이번에 만들지 않는 항목과 그 이유. 필요해지면 별도 기능으로 다룬다.

### 태그 활용 기능

- **태그로 노트 검색·필터링**: 검색/필터 UI, 쿼리 파라미터(json-server `tags_like` 등) 연동 모두 제외.
- **태그별 노트 목록 / 태그 클릭 이동**: 칩은 편집기 안에서 표시·삭제 용도로만 쓰며 클릭 동작이 없다.
- **태그별 개수 집계 / 인기 태그 통계**.
- **전체 태그 목록 화면, 태그 관리 화면**.

### 입력 편의 기능

- **태그 자동완성 / 기존 태그 추천**.
- **쉼표·공백·붙여넣기 기반 다중 태그 일괄 입력**: 쉼표는 이름에 허용되는 일반 문자이며 구분자가 아니다. Enter만 추가 동작이다.
- **태그 순서 변경(드래그 앤 드롭 등)**: 추가한 순서를 유지할 뿐이다.
- **태그 이름 수정(칩 인라인 편집)**: 수정은 삭제 후 재추가로 대체한다.
- **저장 시 입력창에 남은 미확정 텍스트의 자동 태그화**: 저장하지 않고 버린다.

### 데이터·서버

- **별도 `/tags` 리소스 / 정규화된 태그 테이블**: 태그는 노트에 포함된 문자열 배열이다.
- **태그 이름 일괄 변경, 병합, 전체 삭제**.
- **`db.json` 기존 데이터 마이그레이션**: 일괄 수정하지 않고 읽을 때 `[]`로 간주한다.
- **추가/삭제 즉시 서버 반영(낙관적 업데이트 포함)**: 저장 버튼에서 일괄 저장한다.

### 표시·스타일

- **목록 카드(`NoteItem`)의 태그 배지 표시**.
- **읽기 전용 노트 상세 화면**.
- **태그 색상 / 아이콘**.
- **기존 컴포넌트의 일괄 스타일 변환**: 태그 UI에 쓰는 토큰만 사용한다.

### 제한·정책

- **노트당 태그 개수 상한**: 두지 않는다. 길이 상한(15자)만 둔다.
- **중복·길이 초과·빈 값에 대한 사용자 알림(`alert`, 토스트, 에러 문구)**: 중복/빈 값은 조용히 무시한다.
- **저장 실패 시 사용자 안내**: 기존 방식대로 `console.error`만 남긴다.
- **태그 변경 이력, 되돌리기(undo)**.
- **다국어 지원, 사용자별 태그 권한**: UI 텍스트는 한국어 고정이며 사용자 개념이 없다.

### 품질·인프라

- **서버 측 검증**: json-server 기반이라 중복·길이 검증은 클라이언트에서만 한다.
