# tdd-refactor

`/tdd-green`으로 테스트가 통과한 코드를 **동작은 그대로 두고 구조만 개선**한다. TDD의 Refactor 단계다.

테스트가 계속 통과한다는 것이 "동작이 변하지 않았다"는 유일한 증거다. 그래서 한 번에 하나씩 바꾸고 매번 테스트를 돌린다. 여러 변경을 묶으면 테스트가 깨졌을 때 어느 변경이 원인인지 알 수 없고, 롤백 범위도 커진다. 또 강의용 프로젝트라서 요청받지 않은 기능이나 범위 밖 정리는 학습 흐름을 흐트러뜨린다.

## 입력

`$ARGUMENTS` = 이슈 번호 `N`. 없으면 사용자에게 번호를 묻는다. 이슈 번호는 보고서 제목과 시나리오 문서(`docs/features/*/issue-{N}.md`) 참조에만 쓰고, 대상 파일 범위는 4단계의 git diff가 정한다.

## 제약

- **수정 가능: 3단계 git diff로 추출한 `src/` 파일(테스트 파일 제외)만.**
- 새 기능을 추가하지 않는다. 외부에서 관찰되는 동작(렌더 결과, API 호출, props/함수 시그니처의 의미)을 바꾸지 않는다.
- 테스트 파일(`*.test.ts`, `*.test.tsx`)은 수정하지 않는다. 리팩토링 때문에 테스트를 고쳐야 한다면 그 변경은 동작 변경이라는 신호이므로 취소하고 다른 접근을 택한다.
- `src/` 밖(`docs/`, `package.json`, `db.json`, 설정 파일 등)은 수정하지 않는다.
- diff 범위 밖 파일은 수정하지 않는다. 범위 밖에 개선할 곳이 보이면 수정하지 말고 보고서의 "참고" 항목에만 적는다.
- 패키지를 설치하지 않는다. 커밋하지 않는다(사용자가 요청할 때만). `--no-verify` 같은 훅 우회는 하지 않는다.
- `src/`의 `.ts/.tsx/.css`를 수정하면 PostToolUse 훅이 스타일 검사를 돌린다. 신규 위반 피드백이 오면 같은 턴에 고친다. baseline을 갱신해서 숨기지 않는다.

## 실행 순서

### 1. 컨벤션 파악

`CLAUDE.md`를 읽는다. 특히 "구현 패턴 / 컨벤션"(컴포넌트, 상태 관리, API 호출, 네이밍, 스타일), "일관성이 없는 부분", 커밋 규칙을 확인한다. 스타일 작업이 걸려 있으면 `docs/design-system/principles.md`의 Do / Don't도 따른다. 프로젝트 컨벤션이 범용 취향보다 우선이다. 이 프로젝트가 일부러 택한 패턴(예: Context 값 비메모이제이션, `useReducer` 미사용)을 "개선"하지 않는다.

"일관성이 없는 부분"에 적힌 기존 문제는 이번 이슈 diff에 포함된 파일일 때만 후보가 된다.

### 2. 시작 상태 확인

`npm test`를 실행한다. **전체가 통과해야 시작**한다. 실패가 있으면 리팩토링하지 않고 중단해 사용자에게 보고한다(`/tdd-green`을 먼저 끝내야 한다). 기준선을 알아야 이후 실패가 내 변경 때문인지 판단할 수 있으므로, 통과·실패 수(`Tests`)를 기록해 둔다.

### 3. 대상 파일 식별

```bash
git diff main...HEAD --name-only -- src/
```

- 테스트 파일(`*.test.ts`, `*.test.tsx`)을 제외한다.
- 남은 파일이 이번 이슈의 **허용 범위**다. 이 목록을 기억해 두고 이후 모든 수정이 목록 안에 있는지 확인한다.
- 목록이 비어 있으면(브랜치에 변경 없음, `main`이 없음 등) 추측하지 말고 사용자에게 보고하고 멈춘다.
- 커밋하지 않은 변경도 이슈에 속하면 `git status --short -- src/`로 함께 확인해 보고서에 별도 표시한다. 허용 범위에 넣을지는 사용자에게 묻는다.

### 4. 점검

허용 범위의 각 파일을 읽고, 해당 파일을 사용하는 테스트도 읽어 **무엇이 동작으로 고정되어 있는지** 파악한다(고정되지 않은 동작은 리팩토링 중 깨져도 테스트가 알려주지 못하므로 특히 조심한다). 아래 기준으로 검토한다.

| 기준            | 질문                                                                                                                            |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 중복 제거       | 같은 로직·JSX·상수가 반복되는가                                                                                                 |
| 네이밍 명확성   | 이름이 의도를 드러내는가 (`data`, `tmp`, `handle1` 같은 이름)                                                                   |
| 단일 책임       | 한 함수/컴포넌트가 너무 많은 일을 하는가                                                                                        |
| 불필요한 복잡도 | 매직 넘버/문자열, 과도한 중첩, 쓰임이 하나뿐인 추상화                                                                           |
| 컨벤션 불일치   | `CLAUDE.md`의 패턴과 어긋나는가 (named export, `useNotes()`로만 데이터 접근, `handle`/`on` 접두사, 토큰 클래스, 한국어 주석 등) |

후보마다 아래를 정한다. 기준에 걸린다고 모두 고칠 가치가 있는 것은 아니다. 얻는 이득이 변경 위험보다 작으면 후보에서 뺀다.

- 파일과 위치(`path:line`)
- 해당 기준과 문제 설명 한 줄
- 제안하는 변경
- 위험도(낮음/중간/높음)

### 5. 목록 보고 → 승인 대기

후보 목록을 개발자에게 보고하고 **승인을 기다린다.** 승인 전에는 아무 파일도 수정하지 않는다. 사용자가 일부만 승인하면 그 항목만 진행한다. 후보가 없으면 "리팩토링할 항목 없음"으로 보고하고 끝낸다(억지로 만들지 않는다).

보고 형식:

```
## 리팩토링 대상 (이슈 #N)
허용 범위: src/a.ts, src/b.tsx
기준선: npm test 통과 X개

| # | 파일:위치 | 기준 | 문제 | 제안 | 위험도 |
|---|---|---|---|---|---|
| 1 | ... | 중복 제거 | ... | ... | 낮음 |

참고(범위 밖, 수정하지 않음): ...
어떤 항목을 진행할까요?
```

### 6. 하나씩 변경 → 테스트

승인된 항목을 **하나씩** 처리한다.

1. 허용 범위 안의 파일인지 확인하고 변경을 적용한다. 범위 밖 파일이 필요해지면 멈추고 사용자에게 묻는다.
2. `npm test`를 실행한다.
3. 기준선과 같은 수가 통과하면 다음 항목으로 간다. 테스트 수가 줄었다면(파일 collect 실패 등) 실패와 같게 취급한다.

### 7. 실패 시 즉시 롤백

테스트가 하나라도 깨지면 계속 진행하지 않고 **그 변경만 즉시 되돌린다.** 이미 통과를 확인한 앞선 변경은 유지해야 하므로 `git checkout -- <파일>`이나 `git stash`처럼 파일 전체를 되돌리는 방법은 쓰지 않는다. 방금 한 Edit를 역으로 적용해 되돌린 뒤 `npm test`로 기준선 복귀를 확인한다.

그다음 **다른 접근**을 시도한다(더 작은 단위로 쪼개기, 다른 이름, 추출 범위 축소 등). 같은 항목은 최대 2번 다른 접근을 시도하고, 그래도 깨지면 해당 항목을 건너뛰고 보고서에 이유(어떤 테스트가 왜 깨졌는지)를 남긴다. 테스트를 고쳐서 통과시키지 않는다.

### 8. 최종 확인

모든 항목을 끝낸 뒤:

- `npm test`로 전체 통과 수가 기준선과 같은지 확인한다.
- `npm run lint`는 `--fix`로 파일을 자동 수정하므로 범위 밖 파일을 건드릴 수 있다. 대신 `npx eslint <허용 범위 파일>`과 `npx tsc --noEmit`으로 확인만 한다.
- `git status --short`로 수정된 파일이 모두 허용 범위의 `src/` 파일인지 확인한다. 범위 밖 변경이 있으면 원인을 찾아 되돌린다.

### 9. 변경 요약

리팩토링 전후를 요약한다.

```
## 리팩토링 결과 (이슈 #N)
- 테스트: 전 X개 통과 → 후 X개 통과
- 적용한 변경
  1. src/a.ts — 중복 제거: ...
     전: (핵심 코드 몇 줄)
     후: (핵심 코드 몇 줄)
- 건너뛴 항목과 이유
- 참고(범위 밖 개선 후보, 수정하지 않음)
- 수정 파일: ...
- 다음 단계: 다음 이슈 또는 커밋(커밋 규칙은 CLAUDE.md 참고)
```

## 하지 말 것

- 승인 전 수정, 승인되지 않은 항목 수정
- 새 기능·옵션·props 추가, 동작 변경
- 테스트 파일 수정, `it.skip`/`it.todo` 처리
- `src/` 밖 또는 diff 범위 밖 파일 수정
- 여러 변경을 묶어서 한 번에 적용
- 테스트가 깨진 채로 다음 항목으로 넘어가기
- 프로젝트가 의도한 패턴을 범용 취향으로 바꾸기, 쓰임이 하나뿐인 추상화 만들기
- `npm run lint`(자동 수정) 실행, baseline 갱신
