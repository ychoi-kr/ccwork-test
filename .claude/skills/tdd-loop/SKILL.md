# tdd-loop

이슈 1개를 TDD 7단계로 끝까지 진행하는 **순서 보장용 컨테이너**다. 새로운 판단이나 승인 절차를 만들지 않는다. 각 단계는 이미 있는 스킬/에이전트를 그대로 호출하고, 그 안의 개발자 승인 게이트가 그대로 작동한다.

컨테이너가 자체 게이트("다음 단계 진행할까요?")를 만들지 않는 이유: 승인은 각 단계 안에서 이미 받고 있다. 게이트가 겹치면 같은 내용을 두 번 승인하게 되어 사이클이 느려지고, 어느 승인이 어느 단계의 것인지 흐려진다. 대신 사용자가 응답하지 않으면 다음 단계가 시작될 수 없는 구조(각 단계가 승인 대기로 끝남)에 맡긴다.

`$ARGUMENTS` = GitHub 이슈 번호 `N`. 숫자가 아니거나 없으면 번호를 물어보고 멈춘다. 아래에서 `N`은 이 번호다.

## 진행 규칙

- 단계 사이에는 한 줄 진행 메시지만 출력한다. 예: `▶ [2/7] /tdd-red 13 시작`, `✔ [2/7] /tdd-red 완료`
- 단계가 실패하거나 중단되면 `■ 중단: [단계 번호/이름] — 사유`를 출력하고 그 자리에서 멈춘다. 건너뛰거나 임의로 우회하지 않는다. 어디서 멈췄는지가 재개의 유일한 단서이기 때문이다.
- 단계 스킬이 개발자 승인을 기다리며 끝나면(승인 대기 보고), 그 보고를 그대로 전달하고 사용자 응답을 기다린다. 응답(승인 또는 수정 요청)이 오면 같은 단계를 그 응답과 함께 다시 호출한다. 단계가 완료되기 전에는 다음 단계로 넘어가지 않는다.
- 사용자가 단계를 건너뛰거나 순서를 바꾸자고 하면 이유를 한 줄로 확인하고 따른다(프로젝트 TDD 사이클 규칙).

## 단계 0. 사전점검

하나라도 실패하면 알리고 중단한다. 이후 단계는 이 점검이 전부 통과해야 시작한다. 잘못된 브랜치나 더러운 작업 트리에서 시작하면 다른 작업이 이슈 변경에 섞여 들어가기 때문이다.

1. `gh issue view N` — 이슈 본문과 AC를 확인한다. 이슈가 없거나 닫혀 있으면 중단한다. AC가 없으면 알리고 중단한다(이후 `@ac-verifier`가 기준으로 삼는다).
2. `git status --porcelain` — 출력이 있으면(uncommitted changes) 중단한다. 안전을 위해 커밋/스태시를 대신 해 주지 않는다.
3. 현재 브랜치가 `feature/<spec>` 형태인지 확인한다. 아니면 중단하고, 현재 브랜치명과 "feature 브랜치에서 실행해야 한다"는 점을 알린다. 이후 `<spec>`은 이 브랜치명에서 뽑는다.
4. 이슈 브랜치 이름을 정한다: `feat/<N>-<slug>`. slug는 이슈 제목에서 영문·숫자 단어를 소문자 하이픈으로 이은 것이고, 영문이 없으면 `feat/issue-<N>`을 쓴다(한글 제목은 브랜치명에 부적합하다). 이슈 번호로 시작하는 `feat/<N>-*` 또는 `feat/issue-<N>`이 이미 있는지 `git branch --list`로 확인한다.
   - **있으면**: 같은 이슈의 재실행으로 보고 사용자에게 묻는다. (a) 기존 브랜치를 지우고 `feature/<spec>`에서 새로 시작(덮어쓰기), (b) 취소. 사용자 답 전에는 아무것도 바꾸지 않는다. 덮어쓰기를 고르면 지울 브랜치의 미병합 커밋 여부를 먼저 보여 준다.
   - **없으면**: `git switch -c <이슈 브랜치>`로 현재 feature 브랜치에서 분기해 체크아웃한다.

## 단계 1~7

각 단계를 아래 호출 그대로 실행한다. 각 스킬의 상세 동작과 게이트는 해당 스킬 문서가 정한다.

| #   | 호출                 | 이 단계에서 일어나는 것                                                                                                                                                                                                                |
| --- | -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `/test-scenarios N`  | 시그니처 승인 게이트 → 시나리오 승인 게이트. `context: fork`라 승인 지점마다 끝나므로, 사용자의 응답을 받아 `/test-scenarios N 승인` 또는 `/test-scenarios N <수정 요청>`으로 다시 호출한다. 문서의 `상태: 완료`가 될 때까지 반복한다. |
| 2   | `/tdd-red N`         | 시나리오 → 실패 테스트. 테스트가 collect 단계에서 실패하면(import할 대상이 없음) stub 생성을 안내한다.                                                                                                                                 |
| 3   | `/tdd-green N`       | 최소 구현, 회귀 감시. 스킬 내부의 5회 피드백 루프 규칙을 따른다.                                                                                                                                                                       |
| 4   | `@ac-verifier N`     | `Agent` 도구로 `ac-verifier` 에이전트를 호출해 AC 충족을 독립 검증한다.                                                                                                                                                                |
| 5   | `/tdd-refactor N`    | 리팩토링, 변경마다 `npm test`. 깨지면 스킬 규칙대로 즉시 롤백한다.                                                                                                                                                                     |
| 6   | `/security-review N` | `tsc`, `npm audit`, 보안 패턴 점검. 등급(즉시 수정 필요/권장/무시 가능)별 처리 안내를 전달한다.                                                                                                                                        |
| 7   | `/create-pr`         | 아래 "단계 7" 참고.                                                                                                                                                                                                                    |

`/tdd-red`부터는 이슈 번호를 인자로 넘긴다(각 스킬이 번호로 시나리오 문서를 찾는다).

### 단계 4: AC 갭 처리

`ac-verifier`가 충족되지 않은 AC(갭)를 보고하면 그 내용을 그대로 사용자에게 전달하고 **거기서 멈춘다**. 갭이 있는 상태로 리팩토링하면 미완성 코드가 굳기 때문이다. 사용자가 지시하면(구현 보완 후 `/tdd-green`부터 재진행, 또는 갭을 수용하고 계속) 그에 따른다. 갭이 없으면 5단계로 간다.

### 단계 7: 커밋과 PR

`/create-pr`는 변경사항이 커밋되어 있어야 PR 초안을 만들 수 있다. 커밋이 아직 없으면 `/create-pr`를 부르기 전에 다음을 처리한다.

1. 커밋 메시지를 commitlint 규칙에 맞게 작성한다(`type: 제목`, 빈 줄, **비어 있지 않은 본문 2줄 이상**, 시스템이 지정한 attribution 줄). type은 `feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `style`, `perf`, `build`, `ci`, `revert` 중에서 고른다.
2. `printf '%s\n' "<메시지>" | npx commitlint`로 통과를 확인한 뒤 커밋한다. 실패하면 메시지를 고쳐 다시 확인한다. `--no-verify`로 우회하지 않는다. husky pre-commit(lint-staged)이 실패하면 사유를 알리고 중단한다.
3. `/create-pr --base feature/<spec>`을 호출한다. PR base는 반드시 단계 0에서 확인한 feature 브랜치다.
4. PR 본문에 `Closes #N`이 들어가야 한다. `/create-pr`가 만든 초안에 없으면 초안에 추가해 승인 요청에 포함한다. (`/create-pr`의 승인 게이트와 E2E 게이트는 그대로 작동한다. E2E가 실패하면 PR은 만들어지지 않고 이 단계에서 중단한다.)
5. PR이 만들어지면 이슈에 PR 링크를 코멘트로 남긴다: `gh issue comment N --body "PR: <URL>"`.

## 마지막 보고

사이클이 끝나면 다음을 한 번에 요약한다: 이슈 번호, 이슈 브랜치, 각 단계 결과(통과/갭/경고), PR 링크. 이어서 할 일(PR 리뷰·머지)은 제안만 하고 실행하지 않는다.
