# tdd-green

`/tdd-red`가 만든 **실패하는 테스트를 통과시키는 최소한의 구현**을 쓴다. TDD의 Green 단계다.

"최소한"이 핵심인 이유: 테스트가 요구하지 않은 코드는 검증되지 않은 코드이고, 다음 Refactor 단계와 강의 흐름(기능을 단계적으로 추가)을 흐트러뜨린다. 테스트를 통과시키는 데 필요한 만큼만 쓰고, 그 이상은 다음 이슈의 테스트가 요구할 때 쓴다.

## 입력

`$ARGUMENTS` = 이슈 번호 `N`. 없으면 사용자에게 번호를 묻는다.

시나리오 문서는 `docs/features/{feature}/issue-{N}.md`다. `{feature}`는 `docs/features/*/issue-{N}.md`를 찾아 정한다(현재는 `tag`). 후보가 여러 개면 사용자에게 묻는다.

## 제약

- **수정 가능: `src/`의 구현 코드, 시나리오 문서의 체크박스.**
- **테스트 파일(`*.test.ts`, `*.test.tsx`)은 수정하지 않는다.** 테스트가 틀렸다고 판단되면 고치지 말고 사용자에게 보고한다. 기대값을 구현에 맞추면 Red에서 확정한 명세가 무너진다.
- 테스트에 없는 기능, 불필요한 추상화(공용 헬퍼, 미래를 위한 옵션, 일반화)는 만들지 않는다.
- 시그니처는 시나리오 문서와 테스트의 import·호출 형태 그대로 따른다. 이름·경로·인자 순서를 임의로 바꾸지 않는다.
- 패키지를 새로 설치하지 않는다. 커밋하지 않는다(사용자가 요청할 때만). `--no-verify` 같은 훅 우회는 하지 않는다.
- `db.json`은 앱을 실행하면 바뀌므로 건드리지 않는다.

## 실행 순서

### 1. 현재 상태 확인

`npm test`를 실행해 실패 테스트 목록(파일, 테스트 이름, 실패 이유)을 파악한다. 출력된 `Tests` 수를 기록해 둔다(2단계에서 쓴다).

### 2. collect 실패 감지

import 대상 모듈이 없으면 그 테스트 파일은 **개별 테스트가 실행되지 않고 파일 단위로 실패**한다. 이러면 `Tests` 수에 그 파일의 테스트가 빠져 실제 실패 목록이 줄어 보인다. 그래서 먼저 전체가 인식되는지 대조한다.

1. 시나리오 문서 `docs/features/{feature}/issue-{N}.md`의 체크박스(`- [ ]` + `- [x]`) **총 건수**를 센다.
2. vitest가 보고한 `Tests` 수(통과 + 실패)와 비교한다. 이슈 번호와 무관한 기존 테스트가 섞여 있으면 이 이슈의 테스트 파일만 실행해서 비교한다(`npx vitest run <파일>`).
3. **불일치하면** import 대상 모듈이 없는 것이다. 실패 메시지의 `Failed to resolve import` / `Cannot find module`을 보고, **시그니처만 있는 stub 파일**을 만든다.
   - 위치·이름·export는 테스트의 import와 시나리오 시그니처 그대로.
   - 본문은 비운다: 함수는 `throw new Error('Not implemented')`나 타입에 맞는 빈 반환, 컴포넌트는 `return null`. 로직은 쓰지 않는다. stub의 목적은 오직 테스트가 collect되어 개별 실패로 보이게 하는 것이다.
4. `npm test`를 다시 실행해 `Tests` 수가 체크박스 수와 맞는지 확인한다. 여전히 어긋나면 남은 import 실패를 같은 방식으로 해결한다. 그래도 맞지 않으면(체크박스 문서와 테스트 개수가 원래 다른 경우) 사용자에게 보고한다.

### 3. 디자인 컨텍스트 로드

UI 컴포넌트를 구현할 때만 해당한다(훅·api·context만 구현하면 건너뛴다).

- 이 프로젝트의 디자인 문서는 `docs/design-system/`이다. `README.md` 인덱스를 먼저 읽고, 구현할 컴포넌트에 필요한 문서만 골라 읽는다(색 `colors.md`, 간격 `spacing.md`, 글자 `typography.md`, 입체감 `elevation.md`, 컴포넌트별 스펙 `components/`). 단일 파일 `docs/design-system.md`가 있으면 그것을 읽는다.
- 시나리오 문서(`issue-{N}.md`)에 `디자인 참고` 섹션이 있으면 함께 확인한다.
- `CLAUDE.md`의 스타일 컨벤션과 `docs/design-system/principles.md`의 Do / Don't를 따른다. 토큰 클래스(`bg-card`, `text-muted-foreground` 등)를 쓰고, 하드코딩 hex/rgba·인라인 `style`·`shadow-[...]`·1px 실선 구분은 쓰지 않는다.
- 디자인 문서가 없으면 이 단계를 건너뛰고 `CLAUDE.md` 컨벤션만 따른다.

### 4. 첫 번째 실패 테스트를 통과시키는 최소 코드

실패 테스트를 **하나씩, 시나리오 순서대로** 다룬다. 한꺼번에 구현하면 어떤 코드가 어떤 테스트를 위한 것인지 흐려지고 최소 구현에서 벗어나기 쉽다.

- 테스트가 단언하는 동작과 시그니처만 만족시키는 가장 단순한 코드를 쓴다. 하드코딩으로 통과시킬 수 있는 첫 테스트는 그렇게 시작하고, 다음 테스트가 일반화를 요구할 때 일반화한다.
- UI 컴포넌트는 테스트가 요구하는 동작을 충족하면서 3단계에서 읽은 디자인 스펙(Tailwind 클래스, 레이아웃 구조, 상태별 표현)을 **문서에 적힌 그대로** 적용한다. 문서에 없는 시각 요소(아이콘, 장식, 애니메이션 등)를 임의로 추가하지 않는다.
- 프로젝트 컨벤션(`CLAUDE.md`)을 따른다: named export 함수형 컴포넌트, `useNotes()`로만 데이터 접근, 한국어 UI 텍스트·주석, Prettier 규칙.
- `src/`의 `.ts/.tsx/.css`를 수정하면 PostToolUse 훅이 스타일 검사를 돌린다. 신규 위반 피드백이 오면 같은 턴에 고친다. baseline을 갱신해서 숨기지 않는다.

### 5. 통과 확인 + 회귀 확인 (피드백 루프)

1. 방금 다룬 테스트만 실행해 통과를 확인한다: `npx vitest run <파일> -t "<테스트 이름>"`
2. 이어서 `npm test`로 **전체**를 돌려 이전에 통과하던 테스트가 깨지지 않았는지 확인한다.
3. 실패하면 에러 메시지를 읽고 원인을 분석해 구현을 고친 뒤 1번부터 다시 한다. **최대 5회**까지 반복한다.
4. 5회 후에도 실패하면 **중단**하고 사용자에게 보고한다: 어떤 테스트인지, 시도한 수정, 마지막 에러, 의심되는 원인(테스트 자체의 문제 가능성 포함). 테스트를 고쳐서 넘어가지 않는다.

### 6. 체크박스 갱신

통과한 시나리오에 해당하는 `docs/features/{feature}/issue-{N}.md`의 항목을 `- [ ]` → `- [x]`로 바꾼다. 테스트가 통과한 항목만 체크하고, 시나리오 문서의 다른 내용은 건드리지 않는다.

### 7. 다음 실패 테스트로

실패 테스트가 남아 있으면 4단계로 돌아간다.

### 8. 커버리지 측정

전체 통과 후 한 번만 실행한다.

```bash
npx vitest run --coverage
```

- 미커버 라인을 확인하고, **시나리오에서 빠진 케이스인지** 사용자에게 보고한다(예: 에러 분기, 경계값).
- **커버리지를 올리려고 테스트를 추가하지 않는다.** 시나리오 승인 범위를 벗어나는 일이고, 이 수치는 시나리오 누락을 찾는 참고 자료일 뿐이다.
- 미커버 라인을 채우려고 구현을 줄이거나 늘리지도 않는다.

### 9. 결과 요약

보고 항목:

- 구현·수정한 파일 목록(stub로 시작한 파일 표시)
- 체크한 시나리오 수 / 전체 (`- [x]` 건수)
- `npm test` 최종 결과(통과·실패 수)
- 커버리지 요약과 미커버 라인 → 시나리오 누락 후보
- 중단했다면 그 이유와 남은 실패 테스트
- 적용한 디자인 문서와, 디자인 문서에 없어서 비워 둔 시각 요소
- 다음 단계: 리팩터링(Refactor) 또는 다음 이슈

## 하지 말 것

- 테스트 파일 수정, `it.skip`/`it.todo` 처리, 기대값 변경
- 테스트에 없는 기능 선구현, 불필요한 추상화
- 디자인 문서에 없는 시각 요소 추가, 기존 컴포넌트 일괄 스타일 변환
- 커버리지를 위한 테스트 추가
- 5회 실패 후 계속 시도하기(보고하고 멈춘다)
