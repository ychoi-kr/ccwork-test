# e2e-write

PRD의 사용자 스토리를 **실제 브라우저에서 사용자가 겪는 흐름**으로 옮긴다. Playwright + 실제 json-server를 쓴다.

E2E는 느리고 깨지기 쉬운 대신 단위 테스트가 구조적으로 못 보는 것(실제 브라우저 동작, 실제 네트워크 왕복, 컴포넌트들의 실제 연결)을 잡는다. 그래서 이 스킬의 핵심은 "무엇을 쓸까"보다 **"무엇을 쓰지 않을까"** 를 고르는 것이다. 단위 테스트와 같은 것을 E2E로 또 검증하면 비용만 늘고 실패 원인은 흐려진다.

## 입력

`$ARGUMENTS` = 기능명(`docs/features/` 아래 폴더명). 없으면 어떤 기능인지 묻는다.

## 제약

- **생성·수정 가능: `e2e/` 아래 파일뿐.** (`*.spec.ts`, `e2e/support/*`)
- `src/`, 기존 Vitest 테스트, `playwright.config.ts`, `db.json`은 수정하지 않는다. 로케이터를 잡을 수단이 없는 UI는 고치지 말고 보고한다(아래 4단계).
- 패키지를 설치하지 않는다. 커밋하지 않는다(사용자가 요청할 때만).
- 각 단계 사이의 승인 게이트를 지킨다(프로젝트 규칙: 자동으로 다음 단계로 넘어가지 않는다).

## 실행 순서

### 1. 읽기

- `docs/features/{기능명}/prd.md`의 **사용자 스토리 표**(ID, 스토리, 인수 조건)와 **Out of Scope**.
- 기존 테스트: `src/**/*.test.{ts,tsx}`의 `describe`/`it` 이름 목록(`grep -hE "^\s*(describe|it)\(" ...`). 이게 "이미 검증된 것"의 목록이다.
- 화면 코드(`src/layout/`, `src/notes/`, `src/tags/`)에서 버튼 텍스트, `aria-label`, placeholder, 제목 문구를 확인한다. 로케이터와 기대 문구는 추측하지 말고 코드에서 가져온다.
- `playwright.config.ts`(baseURL, `workers: 1`, webServer)와 `e2e/`의 기존 파일. 이미 있는 헬퍼·fixture는 재사용한다.
- **이슈 진행 상태**: `docs/features/{기능명}/issues.md`의 이슈 ↔ 스토리 매핑과, 각 이슈가 구현·머지됐는지(`git log --oneline`, 브랜치/PR, `src/` 코드, 해당 이슈의 단위 테스트 유무)를 확인한다. PRD의 스토리가 전부 구현된 것은 아니다. 아직 구현 전인 이슈의 스토리를 모르고 E2E로 옮기면 "앱 버그"처럼 보이는 실패를 만든다.
- PRD에 "E2E는 Out of Scope"라고 적혀 있어도 사용자가 이 스킬을 불렀다면 사용자 결정이 우선이다. 보고에 한 줄만 언급한다.

### 2. 스토리 분류 → 사용자 승인

인수 조건을 하나씩 **E2E / 단위에 위임 / 제외** 중 하나로 분류한 표를 만들어 보여주고 승인을 받는다. 승인 전에는 코드를 쓰지 않는다.

분류 기준 — E2E에 남기는 것은 아래 중 하나에 해당할 때뿐이다.

| E2E로 쓴다                                                                                            | 이유                                                             |
| ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 저장 후 **새로고침/재진입해도 남아 있음** (실제 json-server 왕복)                                     | 단위 테스트는 `fetch`/Context를 mock하므로 서버 영속성을 못 본다 |
| 사용자의 **여러 단계 여정** (선택 → 편집 → 저장 → 목록 반영)                                          | 컴포넌트·Context·API 연결 오류는 조각 테스트로 안 잡힌다         |
| **실제 브라우저에서만 의미 있는 동작** (hover/`focus-visible`로 보임, 실제 키보드 Tab 순서, IME 조합) | jsdom은 CSS 가시성·포커스 링·IME를 재현하지 못한다               |
| 취소/저장 같은 **화면 전환과 서버 상태의 일치**                                                       | 화면과 서버가 어긋나는 버그는 둘을 함께 볼 때만 드러난다         |

| 단위에 위임한다 (E2E에서 쓰지 않는다) | 예                                                                |
| ------------------------------------- | ----------------------------------------------------------------- |
| 입력 규칙의 경우의 수                 | 대소문자/공백 정규화 변형, 빈 값, `maxLength`, 중복 판정 조합     |
| 콜백·props·인자 검증                  | `onAdd` 호출 인자, `preventDefault`, PATCH 본문 모양              |
| 에러·예외 분기                        | `updateNote` 실패 시 `console.error` 등 (mock이 필요한 실패 주입) |
| 한 컴포넌트 안의 렌더링               | 칩 순서, `aria-label` 문자열 자체                                 |

판단이 애매하면 이렇게 묻는다: _"이 검증이 실패했을 때 단위 테스트는 못 잡고 E2E만 잡는가?"_ 아니라면 위임한다. 같은 스토리라도 대표 경로 1개만 E2E로 두고 변형은 단위에 맡긴다(예: 중복 방지는 `react` 하나만 확인, 대소문자 조합 전부는 아님).

**구현 전 스토리**: 이슈가 아직 구현되지 않은 스토리는 기본적으로 **보류**로 분류하고 표의 근거란에 이슈 번호를 적는다. 구현이 없으면 단위 테스트도 없어서 "단위에 위임"할 수 없고, E2E가 그 역할을 대신하면 안 된다. 사용자가 인수 기준을 먼저 E2E로 박아 두자고 하면(Red 용도) 작성하되 `test.fixme`로 막고(아래 "하지 않는 것"), 보고에 어느 이슈가 풀어 줄지 적는다.

표 형식:

| 스토리/AC | 분류 | 근거(기존 단위 테스트 이름 또는 "서버 왕복 필요" 등) | E2E 시나리오 |
| --------- | ---- | ---------------------------------------------------- | ------------ |

시나리오는 보통 **스토리당 0~1개, 전체 5~8개 안쪽**이 적정선이다. 많아지면 위임 기준을 다시 적용한다.

### 3. 지원 코드 준비

`e2e/support/`에 필요한 것만 만든다(이미 있으면 재사용). 구체 코드는 [references/patterns.md](references/patterns.md)를 읽는다.

- **테스트 데이터 fixture**: 테스트가 만든 노트를 API(`http://localhost:3001/notes`)로 시드하고, 끝나면 `afterEach`에서 삭제한다. `db.json`은 git 추적 파일이고 json-server가 직접 쓰기 때문에, 정리하지 않으면 매 실행마다 저장소가 더러워진다.
- 시드 노트 제목은 고유하게(`e2e-{스토리ID}-{타임스탬프}`) 만든다. 기존 노트(`첫 번째 노트` 등)를 읽거나 수정하는 테스트는 쓰지 않는다. 사용자 데이터에 의존하면 테스트가 개발자 PC마다 달라진다.
- Page Object는 만들지 않는다. 같은 로케이터를 3개 이상 테스트가 반복할 때만 `e2e/support/`에 작은 헬퍼 함수로 뽑는다(이 앱은 화면이 하나라 과하다).

### 4. 테스트 작성 → 하나씩 실행

시나리오 순서대로 하나 쓰고, 그 테스트만 돌려 통과를 확인한 뒤 다음으로 간다.

```bash
npx playwright test e2e/{기능명}.spec.ts -g "US-1"
```

**로케이터가 없을 때**: 사용자 눈에 보이는 이름(역할, 라벨, 텍스트)으로 잡을 수 없는 요소가 있으면(예: 이름 없는 `<input>`), 임의 CSS 셀렉터로 우회하지 말고 해당 시나리오를 멈춘 뒤 보고한다. 제안: `aria-label` 추가(접근성도 개선됨). `src/` 수정은 사용자 승인 후 별도로 한다.

**테스트가 실패할 때**: 테스트를 억지로 맞추기 전에 원인을 구분한다. (a) 테스트 코드 문제 → 고친다. (b) 앱의 실제 버그 → 고치지 말고 보고한다. E2E가 발견한 버그를 테스트를 느슨하게 만들어 숨기면 이 테스트의 존재 이유가 사라진다.

### 5. 안정성 확인

```bash
npx playwright test e2e/{기능명}.spec.ts --repeat-each=3
npx prettier --check e2e && npx eslint e2e
git status --short   # db.json이 바뀌었는지 확인
```

- 3회 연속 통과해야 한다. 한 번이라도 실패하면 flaky로 보고 원인(대기, 데이터 공유, 순서 의존)을 고친다. `retries`나 `waitForTimeout`으로 덮지 않는다.
- `db.json`에 diff가 남으면 정리 누락이다. fixture를 고친다(diff를 되돌리는 것은 사용자에게 확인).
- `npm test`(Vitest)도 돌려 `e2e/`가 섞여 들어오지 않았는지 확인한다.

### 6. 보고

- 만든 파일, 스토리 → 시나리오 매핑, **단위에 위임한 항목과 이유**
- 실행 결과(통과 수, `--repeat-each=3` 결과), `db.json` 변경 여부
- 막힌 항목(로케이터 부재, 발견한 앱 버그)
- 다음 제안: 필요한 경우에만 (예: aria-label 추가, CI에 `test:e2e` 연결)

## 작성 규칙 (best practices)

### 구조

- 파일: `e2e/{기능명}.spec.ts`, 공용 코드: `e2e/support/`. named import, 파일명 소문자/camelCase.
- 테스트 제목은 한국어, 스토리 ID로 시작: `test('US-3: 태그 칩의 X를 누르면 해당 태그만 삭제된다', ...)`. 스토리 ID가 PRD로의 추적 링크다.
- 한 테스트는 한 가지 사용자 목적을 끝까지 따라간다. 테스트끼리 순서·상태를 공유하지 않는다(어느 것을 단독 실행해도 통과해야 한다).
- 코드 주석은 한국어, Prettier 규칙(세미콜론, 작은따옴표, 2칸, trailing comma, printWidth 100)을 따른다. `eslint-disable`/`@ts-ignore`로 억제하지 않는다.

### 로케이터

- 우선순위: `getByRole`(+`name`) → `getByLabel` → `getByPlaceholder` → `getByText`. 사용자가 보는 방식 그대로 찾는다.
- CSS 클래스(Tailwind), DOM 구조 의존 셀렉터(`div > span:nth-child`)는 쓰지 않는다. 디자인 수정만으로 깨진다.
- `data-testid`는 위 방법이 모두 불가능하고 `aria-label` 추가도 부적절할 때만, 사용자 승인 후.

### 대기와 단언

- 자동 대기되는 **web-first 단언**만 쓴다: `await expect(locator).toBeVisible()`, `toHaveCount`, `toHaveValue`.
- `page.waitForTimeout`, 고정 `sleep`, `locator.isVisible()` 결과를 `expect(...).toBe(true)`로 비교하는 패턴은 쓰지 않는다. 느리거나 불안정한 원인이 된다.
- 네트워크 완료가 필요하면 화면에 나타나는 결과(목록에 제목이 보임)로 기다린다. 정말 응답 자체가 기준이면 `page.waitForResponse`를 액션 **전에** 걸어 둔다.
- 검증은 사용자가 보는 결과(화면, 새로고침 후 상태)와 서버에 남은 최종 상태로 한다. 내부 상태·호출 횟수는 보지 않는다.

### 데이터와 격리

- API로 시드하고 API로 정리한다. UI로 준비 단계를 반복하면 느리고, 준비 단계 버그가 본 검증을 흔든다. (단, 그 UI 조작 자체가 검증 대상이면 UI로 한다.)
- 서버 상태 확인은 `request` fixture로 `GET /notes/{id}`를 직접 조회한다.
- 외부 서비스·API는 mock하지 않는다. 실패 주입이 필요한 시나리오는 단위 테스트 몫이다.

### 하지 않는 것

- `test.skip`/`test.fixme`로 실패를 감추기(예외: 아직 구현되지 않은 이슈의 스토리를 사용자 승인 아래 먼저 작성한 경우. `test.fixme(조건, '이슈 번호: 사유')` 형태로 이슈 번호를 남기고, 구현이 머지되면 제거한다), 스크린샷 스냅샷 비교(디자인 토큰은 별도 검사 훅이 담당), 모든 브라우저 매트릭스 확장(설정은 Chromium 하나).
