# test-scenarios

이슈 하나를 **시그니처 확정 → 테스트 시나리오 도출 → AC 대조**까지 처리해 `docs/features/tag/issue-{N}.md`로 남긴다. 이 문서가 이후 TDD(테스트 코드 → 구현)의 입력이 된다.

시그니처를 먼저 고정하는 이유: 시나리오의 `함수명`과 `조건`이 시그니처에 묶여 있어야 테스트 코드가 구현 방식에 흔들리지 않는다. 구현 코드를 쓰지 않는 이유: 이 단계의 산출물은 "무엇을 검증할지"이고, 구현이 먼저 나오면 시나리오가 구현을 따라 쓰이기 때문이다. 그래서 **구현 코드와 테스트 코드는 절대 작성하지 않는다**(타입·시그니처 선언만 허용).

## 입력

`$ARGUMENTS` = `<이슈 번호> [승인 | 수정 요청]`. 첫 토큰이 이슈 번호 `N`이다. 나머지는 이전 실행에 대한 개발자의 응답이다.

## 왜 상태를 파일에 두는가

이 스킬은 `context: fork`(서브에이전트)로 실행되어 실행 도중 개발자에게 질문하고 답을 기다릴 수 없다. 그래서 **승인 지점마다 실행을 끝내고 결과를 보고**하며, 진행 상태는 `docs/features/tag/issue-{N}.md` 맨 위의 `상태:` 줄에 기록한다. 개발자가 `/test-scenarios N 승인`(또는 수정 요청)으로 다시 부르면 이 줄을 보고 이어간다. 승인 전에는 다음 단계로 넘어가지 않는다.

시작할 때 파일을 확인해 단계를 정한다.

| 파일 상태                                     | 이번 실행에서 할 일                                                                    |
| --------------------------------------------- | -------------------------------------------------------------------------------------- |
| 파일 없음                                     | 단계 A (시그니처 초안)                                                                 |
| `상태: 시그니처 승인 대기` + 인자가 수정 요청 | 시그니처를 수정하고 단계 A의 보고를 다시 한다                                          |
| `상태: 시그니처 승인 대기` + 인자가 `승인`    | 단계 B (시나리오 도출 + AC 대조)                                                       |
| `상태: 시나리오 승인 대기` + 인자가 수정 요청 | 시나리오를 수정하고 단계 B의 보고를 다시 한다                                          |
| `상태: 시나리오 승인 대기` + 인자가 `승인`    | 상태를 `완료`로 바꾸고 끝낸다. 다음은 TDD 테스트 코드 작성이라고 알린다                |
| 인자 없이 파일이 이미 있음                    | 현재 상태를 요약하고 다음에 해야 할 입력(`승인`/수정 요청)을 안내한다. 덮어쓰지 않는다 |

## 단계 A. 시그니처 확정 (승인 대기까지)

1. 읽을 것:
   - `gh issue view N` — 설명, **완료 조건(Acceptance Criteria)**, 이슈에 이미 있는 시나리오(Given/When/Then)와 테스트 메모.
   - `docs/features/tag/prd.md` (필요하면 `spec-fixed.md`, `issues.md`의 해당 이슈 절) — 결정 사항·Out of Scope.
   - 코드베이스: `src/api/notes.ts`, `src/context/NotesContext.tsx`, `src/types/note.ts`, 관련 `src/components/*`, 이미 있는 `src/hooks/*`. 기존 패턴을 그대로 따르려면 실제 코드를 봐야 한다.
2. 이슈가 건드리는 것만 시그니처로 확정한다. 이슈에 없는 기능을 미리 채워 넣지 않는다(이 프로젝트는 강의용이라 일부러 비워 둔 부분이 있다).
3. 확정할 항목:
   - **함수/훅 시그니처**: 이름, 파라미터 타입, 반환 타입. 이름 규칙은 CLAUDE.md를 따른다(`create/update/delete` + `Note`, props 콜백은 `on` + 동작, 구현은 `handle` + 동작, 불리언은 `is`/`-ing`).
   - **에러 케이스**: 어떤 입력·상황에서 throw/무시/`console.error` 중 무엇이 일어나는지. API는 `!res.ok`면 영어 고정 메시지의 `Error`를 throw, 변경 실패는 호출 컴포넌트가 `console.error`만 남기는 기존 정책을 따른다. 이슈가 정책을 바꾸지 않는 한 새 정책을 만들지 않는다.
   - **컴포넌트 Props 타입**: 같은 파일 상단 `interface XxxProps`, `React.FC` 없음, 슬롯은 이름 있는 props.
   - 기존 시그니처가 **바뀌는** 경우 변경 전/후를 나란히 적는다.
4. 확신이 없는 결정(예: 반환 타입 후보가 둘)은 임의로 고르지 말고 **미결 사항**으로 적어 개발자에게 묻는다.
5. `docs/features/tag/issue-{N}.md`를 아래 형식으로 만든다(시나리오 절은 아직 비워 둔다).
6. 최종 응답으로 시그니처 전체와 미결 사항을 보여주고 "검토 후 `/test-scenarios N 승인` 또는 수정 요청을 주세요"라고 끝낸다. 여기서 멈춘다.

## 단계 B. 시나리오 도출과 AC 대조 (승인 대기까지)

1. 파일의 `상태:`를 `시그니처 확정(승인됨)`을 거쳐 최종적으로 `시나리오 승인 대기`로 바꾼다. 승인된 시그니처는 이후 바꾸지 않는다(바꿔야 하면 개발자에게 알린다).
2. 시그니처에서 시나리오를 도출한다. 분류:
   - **정상**: 기대한 입력으로 기대한 결과.
   - **경계**: 길이 한계, 빈 값, 앞뒤 공백, 기존 데이터에 필드 없음, 순서 유지처럼 경계에 있는 입력.
   - **예외**: 시그니처 단계에서 정한 에러 케이스(실패 응답, 잘못된 입력, Provider 밖 호출 등).
3. **형식은 한 줄씩 정확히 이렇게 쓴다**:
   `[정상|경계|예외] 함수명 – should [기대동작] when [조건]`
   `함수명`에는 훅·API 함수·컴포넌트 이름을 쓴다. 구분 대시는 en dash(–)다. 테스트 코드(`it(...)`, `expect`)는 쓰지 않는다.
4. 파일 하단 `## 테스트 시나리오`에 기록한다.
5. **AC 대조**: `gh issue view N`을 다시 읽어 AC 체크리스트를 뽑는다. 각 AC마다 그것을 검증하는 시나리오를 찾아 `## AC 커버리지` 표에 `AC 항목 | 시나리오 번호`로 적는다. 시나리오가 없는 AC는 시나리오를 추가한 뒤 표를 갱신한다. 시나리오로 검증할 수 없는 AC(예: `npm run build`, 린트, 스타일 검사 훅 통과)는 "자동 검사"로 표시하고 이유를 한 줄 적는다. 끝에 모든 AC가 최소 1개 시나리오 또는 "자동 검사"로 덮였는지 확인한 결과를 적는다.
6. 이슈 본문에 이미 있는 Given/When/Then 시나리오는 출발점으로 삼되 그대로 복사하지 않는다. 그것들이 놓친 경계·예외를 찾는 것이 이 단계의 가치다.
7. 최종 응답으로 시나리오 목록과 AC 커버리지 표를 보여주고 "검토 후 `/test-scenarios N 승인` 또는 수정 요청을 주세요"라고 끝낸다. 여기서 멈춘다.

## issue-{N}.md 형식

```markdown
# TAG-{N}. {이슈 제목} — 시그니처와 테스트 시나리오

> 상태: 시그니처 승인 대기
> 근거: GitHub 이슈 #{N}, [`prd.md`](./prd.md)

## 시그니처

### 타입

(`interface`/`type` 선언만)

### 함수 · 훅

(이름, 파라미터, 반환 타입을 선언 형태로. 본문 없음)

### 컴포넌트 Props

(`interface XxxProps`)

### 에러 케이스

| 대상 | 상황 | 동작 |
| ---- | ---- | ---- |

### 미결 사항

(없으면 "없음")

## 테스트 시나리오

(단계 B에서 채운다)

## AC 커버리지

(단계 B에서 채운다)
```

## 하지 말 것

- 구현 코드, 테스트 코드, `src/` 파일 수정. 이 스킬이 쓰는 파일은 `docs/features/tag/issue-{N}.md` 하나뿐이다.
- 이슈·PRD의 Out of Scope 항목에 대한 시그니처/시나리오.
- 승인(`승인` 인자) 없이 다음 단계 진행.
- 문서·시나리오는 한국어로 쓴다(함수명·타입은 코드 그대로).
