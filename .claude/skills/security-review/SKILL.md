# security-review

리팩토링이 끝난 뒤 **커밋 전에** 타입 오류와 보안 취약점을 점검하고, 발견 사항을 심각도별로 분류해 보고한다. TDD 흐름(Red → Green → Refactor) 다음, 커밋 직전의 관문이다.

점검과 수정을 분리하는 이유: 의존성 업데이트나 환경 변수 정리는 빌드와 런타임에 영향을 줄 수 있어서 개발자가 판단해야 한다. 그래서 먼저 수집·분류해 보고하고, 승인된 "즉시 수정 필요" 항목만 고친다.

> 이 이름은 Claude Code 내장 `/security-review`와 같다. 프로젝트 스킬이 우선 적용되는지 확인이 필요하면 사용자에게 알린다. 내장 스킬은 현재 브랜치 변경분 전체를 보는 별도 점검이다.

## 입력

`$ARGUMENTS` = 이슈 번호 `N`. 없으면 사용자에게 번호를 묻는다. 번호는 보고서 제목에만 쓴다. 점검 대상은 이슈와 무관하게 프로젝트 전체(`tsc`, `npm audit`)와 `src/`(.env 노출)이다.

## 제약

- **개발자 승인 전에는 어떤 파일도 수정하지 않는다.** 점검(4단계까지)은 읽기 전용이다.
- 승인 후에도 **"즉시 수정 필요"로 분류되고 승인된 항목만** 고친다. "권장 수정"은 보고만 하고, 사용자가 명시적으로 지시한 항목만 처리한다.
- 판단이 필요한 항목(의존성 메이저 업그레이드, 변수 이름 변경, 코드 동작이 바뀌는 수정)은 처리 방법을 제안하고 승인을 받은 뒤에만 한다.
- **테스트 파일(`*.test.ts`, `*.test.tsx`)은 수정하지 않는다.** 테스트 파일에서 타입 오류가 나오면 고치지 말고 보고한다(원인이 구현 쪽 시그니처라면 구현을 고치는 안을 제안한다).
- **`npm audit fix --force`는 쓰지 않는다.** 호환되지 않는 메이저 업그레이드를 강제로 적용해 앱이 깨질 수 있다. `npm audit fix`(비강제)도 `package.json`/`package-lock.json`을 바꾸므로 승인 후에만 실행한다.
- `.env` 계열 파일의 **값은 출력하지 않는다.** 변수 이름과 위치만 다룬다. 값이 보고서나 대화에 남으면 그 자체가 유출이다.
- 새 패키지를 설치하지 않는다. 커밋하지 않는다(사용자가 요청할 때만). `--no-verify` 같은 훅 우회는 하지 않는다.
- `src/`의 `.ts/.tsx/.css`를 수정하면 PostToolUse 훅이 스타일 검사를 돌린다. 신규 위반 피드백이 오면 같은 턴에 고친다. baseline을 갱신해서 숨기지 않는다.

## 실행 순서

### 1. 타입 오류 수집

```bash
npx tsc --noEmit
```

- 오류를 `파일:줄 — 코드 — 메시지`로 정리한다. 오류가 없으면 "클린"으로 기록한다.
- 이 프로젝트의 `npm run build`는 `tsc && vite build`라서 타입 오류는 곧 빌드 실패다.
- 테스트 파일의 오류도 수집하되 수정 대상에서는 제외한다.

### 2. 의존성 취약점 수집

```bash
npm audit
```

- 취약점이 있으면 종료 코드가 0이 아닐 수 있다. 실패가 아니라 결과이니 출력을 그대로 읽는다.
- 패키지, 심각도(info/low/moderate/high/critical), 취약점 설명, 직접/간접 의존성 여부, 수정 가능 여부(`fix available`, 메이저 변경 여부)를 정리한다.
- 운영 번들에 들어가는 의존성(`dependencies`)인지 빌드·개발 전용(`devDependencies`)인지 `package.json`으로 구분한다. 분류에 쓰인다. 필요하면 `npm audit --omit=dev`로 운영 의존성만 따로 확인한다.
- 네트워크 오류로 레지스트리에 닿지 못하면 결과를 추측하지 말고 "audit 수행 불가(사유)"로 보고한다.

### 3. .env 변수 노출 점검

이 프로젝트는 Vite를 쓰고, 클라이언트 코드에서 읽을 수 있는 환경 변수는 `import.meta.env`다. **`VITE_` 접두사가 붙은 변수는 빌드 결과(JS 번들)에 그대로 포함되어 누구나 볼 수 있다.** 비밀 값이 `VITE_` 변수에 있으면 사실상 공개된 것이다. 아래를 확인한다.

1. 환경 파일 목록: `ls -a`로 `.env*` 파일을 찾고, 변수 **이름만** 추출한다(예: `grep -oE '^[A-Za-z_][A-Za-z0-9_]*' .env`). 값은 출력하지 않는다.
2. `.gitignore`에 `.env`(또는 `.env.local` 등)가 포함되어 있는지, `git ls-files | grep -E '^\.env'`로 **추적되고 있는 `.env` 파일**이 없는지 확인한다(`.env.example`은 값이 비어 있다면 정상).
3. `src/`에서 환경 변수 참조: `grep -rnE "import\.meta\.env|process\.env" src/` (테스트 파일 결과는 따로 표시)
4. 변수 이름 중 `SECRET`, `KEY`, `TOKEN`, `PASSWORD`, `PRIVATE`이 `VITE_` 접두사와 함께 쓰이는지 본다.
5. 하드코딩된 비밀 의심 패턴: `grep -rnEi "(api[_-]?key|secret|token|password|bearer)\s*[:=]\s*['\"][^'\"]{8,}" src/` (매치 내용 중 값은 보고서에 `***`로 가린다)
6. 환경 파일이나 `process.env` 값을 `console.log`로 출력하는 코드가 있는지 본다.

참고: 이 프로젝트의 `API_URL`(`http://localhost:3001`)은 비밀이 아닌 개발용 주소다. 하드코딩이라는 이유만으로 취약점으로 분류하지 않는다(필요하면 "무시 가능" 또는 "권장 수정").

`.env` 파일이 없고 `src/`에서 환경 변수를 쓰지 않으면 "해당 없음(클린)"으로 기록한다.

### 4. 분류하고 보고

수집한 모든 항목을 아래 세 분류 중 하나에 넣어 보고한다. 판단 근거를 한 줄씩 적는다. 분류가 애매하면 더 안전한 쪽(더 높은 심각도)에 두고, 그 이유를 적는다.

| 분류               | 기준                                     | 예                                                                                                                                       |
| ------------------ | ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **즉시 수정 필요** | 보안 위험이거나 빌드 실패 수준           | 구현 코드의 타입 오류(`tsc` 실패), 운영 의존성의 high/critical 취약점, `VITE_` 변수에 담긴 비밀 값, 추적되는 `.env`, 하드코딩된 키·토큰  |
| **권장 수정**      | 당장 깨지지 않지만 품질·보안 수준을 낮춤 | 개발 전용 의존성의 moderate 이하 취약점, `any`로 인한 타입 구멍, 불필요한 `process.env` 참조, 테스트 파일의 타입 오류(수정 불가, 보고만) |
| **무시 가능**      | false positive이거나 의도된 패턴         | 개발 서버에서만 도달하는 취약점으로 실제 경로가 없는 경우, 비밀이 아닌 공개 값의 하드코딩(`API_URL`), `CLAUDE.md`에 의도라고 적힌 패턴   |

"무시 가능"도 **왜 무시해도 되는지**를 적는다. 근거 없이 무시로 분류하지 않는다. 그리고 이 분류는 제안이므로 개발자가 바꿀 수 있다.

보고 형식:

```
## 점검 결과 (이슈 #N)
- tsc: 오류 X건 / audit: Y건 (critical a, high b, moderate c, low d) / .env 노출: Z건

### 즉시 수정 필요 (K건)
1. [tsc] src/a.ts:12 — TS2322 ... → 제안: ...
2. [audit] pkg@1.2.3 (high, 운영 의존성) — ... → 제안: npm audit fix (비강제, 메이저 변경 없음)

### 권장 수정 (K건)
...

### 무시 가능 (K건)
1. ... — 이유: ...

즉시 수정 필요 항목을 진행할까요? (전체 / 번호 선택 / 없음)
```

항목이 모두 클린이면 "클린 — 커밋 가능"으로 보고하고 끝낸다. 억지로 항목을 만들지 않는다.

### 5. 승인 후 "즉시 수정 필요"만 처리

- 승인된 항목을 **하나씩** 고친다. 한 항목을 고칠 때마다 영향이 있는 점검(`tsc`면 `npx tsc --noEmit`)을 다시 돌려 새 오류가 생기지 않았는지 확인한다.
- 타입 오류: 구현 코드(`src/`)만 고친다. 동작이 바뀌는 수정이면 먼저 제안하고 승인을 받는다.
- audit: 비강제 `npm audit fix`를 먼저 제안한다. 메이저 업그레이드가 필요하면 영향(변경될 버전, 깨질 수 있는 API)을 설명하고, 별도 승인을 받아 `npm install <pkg>@<버전>`으로 개별 적용한다. 수정할 방법이 없으면 보고서에 사유를 남기고 넘어간다.
- .env 노출: 비밀 값을 `VITE_` 변수에서 제거하는 것은 서버 측으로 옮겨야 하는 설계 판단이므로 방법을 제안하고 승인받는다. 이미 커밋에 노출된 비밀은 코드 수정만으로 안전해지지 않으니(키 폐기·재발급 필요) 사용자에게 알린다.
- 수정 후 테스트가 깨지면 그 수정을 되돌리고 다른 접근을 제안한다. 테스트를 고쳐서 넘어가지 않는다.

### 6. 재스캔

처리를 마치면 1~3단계를 다시 실행하고, 추가로 `npm test`를 돌려 회귀가 없는지 확인한다. 결과를 처리 전과 비교한다.

- "즉시 수정 필요" 항목이 0건이면 클린이다.
- 남아 있으면 이유(수정 방법 없음, 사용자가 보류 등)와 함께 보고한다.
- 클린이 아닌 채로 "클린"이라고 말하지 않는다.

### 7. 결과 요약

```
## 보안 점검 결과 (이슈 #N)
- 처리 전 → 처리 후: tsc X → X', audit Y → Y', .env Z → Z'
- 수정한 항목과 변경 파일(package.json 포함)
- 남은 항목: 권장 수정 K건, 무시 가능 K건 (필요하면 목록)
- npm test: 통과 X개
- 다음 단계: 커밋 (커밋 규칙은 CLAUDE.md 참고: refactor/fix/chore 등 type, 본문 2줄 이상)
```

## 하지 말 것

- 승인 전 수정, 승인되지 않은 분류의 항목 수정
- `npm audit fix --force`
- 테스트 파일 수정, `// @ts-ignore`/`any`로 타입 오류 덮기, 테스트를 고쳐 통과시키기
- `.env` 값 출력 또는 보고서·대화에 비밀 값 남기기
- 근거 없는 "무시 가능" 분류
- 재스캔 없이 완료 보고, 클린이 아닌데 클린이라고 보고
- baseline 갱신으로 스타일 위반 숨기기
